# Генерация скетчей через ImageGen

Impressor подготавливает изображение предмета по общему шаблону: назначение,
крупные массы, пропорции, ракурс и ограничения прохода. Саму картинку создаёт
ImageGen, который запускает агент. Команда `python -m impressor sketch` собирает
промпт и параметры вызова из YAML; сетевой запрос и генерацию она не выполняет.

Первый скетч показывает programmer art из кубов и прямоугольных блоков.
После выбора компоновки можно уточнять силуэт, конструкцию и материалы,
сохраняя принятую картинку как вход следующего прохода.
По умолчанию новый шаблон показывает шесть ортографических проекций и изометрию
одного объекта по [контракту видов](PROJECTION_CONTRACT.md).
Полный процесс с интерфейсом и промптами есть в [HTML руководстве](../docs/guide/index.html).

## Запрос в чате

Достаточно написать агенту:

> Impressor: сгенерируй лист небольшого грузовика по шаблону, проход cube_massing: front, rear, left, right, top, bottom и изометрия. Кабина, кузов, шасси и кубические заместители колёс. Все панели показывают одну компоновку в согласованном масштабе. Проверяем соотношение кабины и кузова.

Агент записывает задание, собирает запрос, вызывает ImageGen и сохраняет
изображение вместе с промптом. Для другого предмета замени название и перечисли
его основные функции или части. Можно начать с одного предложения:
«Impressor: сгенерируй скетч башни поддержки из кубов»; агент предложит минимальный
набор смысловых масс в задании.

Для повторяемого задания укажи готовый файл:

> Impressor: сгенерируй картинку через ImageGen по impressor/templates/sketch_brief.example.yaml и сохрани результат новой итерацией.

Пример грузовика находится в [задании](templates/sketch_brief.example.yaml),
общие правила изображения — в [шаблоне](templates/sketch_template.yaml).

## Подготовка запроса командой

Из корня проекта:

```bash
.venv/bin/python -m impressor sketch impressor/templates/sketch_brief.example.yaml --out var/impressor/truck_sheet_r001
```

В папке результата появятся:

| Файл | Содержание |
| --- | --- |
| `prompt.txt` | Полный промпт для просмотра или ручной передачи генератору |
| `imagegen_request.json` | Аргументы для встроенного ImageGen |
| `brief.resolved.yaml` | Задание, сохранённое для этой итерации |
| `template.resolved.yaml` | Правила шаблона, использованные при сборке |
| `manifest.json` | Запись подготовки со статусом `prepared` и режимом `built_in_via_agent` |

Для уточнения также сохраняется копия входной картинки `source_image.*`, а её
хэш записывается в manifest. Исходный файл можно менять независимо от сохранённой
итерации. После переноса папки пересобери запрос из `brief.resolved.yaml` в новую
папку: пути к изображениям в аргументах инструмента должны указывать на их новое
местоположение.

Затем попроси агента: «Создай картинку через ImageGen по
`var/impressor/truck_sheet_r001/imagegen_request.json` и сохрани её в эту папку».
Статус `prepared` означает, что запрос готов. Изображение появляется после
вызова ImageGen, а запись `generated` ставится после сохранения результата.

Рабочие итерации удобно хранить в `var/impressor/`: каталог `var/` уже исключён
из Git. Проверенный пример для знакомства с проектом можно хранить отдельно,
как [пример грузовика](examples/truck_cube_r001/).

## Поля задания

Скопируй пример и измени предмет, цель проверки и основные массы. Путь `template`
считается относительно файла задания; при переносе задания в другую папку
поправь этот путь. То же правило действует для `source_image`.

| Поле | Что записывать |
| --- | --- |
| `schema` | `impressor/sketch/v1` |
| `id` | Имя задания, например `truck_cube_r001` |
| `subject` | Предмет, который должен появиться на картинке |
| `purpose` | Его функция и то, что игрок должен распознать |
| `question` | Одно решение, проверяемое этим изображением |
| `pass` | Проход из таблицы ниже |
| `template` | Путь к общим правилам изображения |
| `view_mode` | `projection_sheet` для семи видов; `single` для отдельного иллюстративного ракурса |
| `view_contract` | Контракт `impressor/projections/v1`; новый общий шаблон задаёт его по умолчанию |
| `dimensions` | Для листа обязательны `units: meters`, `axes: gltf_y_up`, положительный `envelope_m: [X, Y, Z]` и числовой `ground_y_m` |
| `masses` | Список крупных функциональных объёмов и их расположения |
| `proportions` | Список отношений размеров, важных для этой гипотезы |
| `preserve` | Список решений, которые нужно сохранить |
| `avoid` | Список нежелательных элементов |
| `source_image` | Принятое изображение для уточнения; для нового скетча поле можно пропустить |
| `change` | Одно требуемое изменение; обязательно при использовании `source_image` |

Например, в `masses` можно записать «Короткая кабина в передней части шасси»
и «Длинный цельный блок кузова за кабиной», а в `proportions` — «Кузов примерно
вдвое длиннее кабины». Это ориентиры для компоновки. Точные размеры назначаются
позже в геометрической записи блокаута.

## Проходы изображения

| Проход | Задача |
| --- | --- |
| `cube_massing` | Только кубы и прямоугольные блоки, нейтральная поверхность, основные пропорции |
| `silhouette` | Уточнить крупные формы и узнаваемость принятой компоновки |
| `structure` | Показать функциональные части, необходимые опоры и стыки |
| `detail` | Добавить полезные детали, видимые с игровой камеры |
| `game_check` | Подготовить визуальный референс материалов и акцентов для сравнения с моделью в игре |

На `cube_massing` шаблон запрещает скосы, цилиндры, окна, мелкую механику,
текстуры и декоративные элементы. Колесо обозначается кубическим заместителем.
В каждой панели один предмет показан целиком на спокойном фоне, без подписей.
В `single` показывается только один ракурс; он не заменяет проверку полного листа.
Сложную форму
разрешают на следующем проходе, когда сформулирована причина её появления.

Картинка `game_check` не подтверждает импорт, анимацию или масштаб в Godot.
Эти проверки выполняются на собранном ассете по
[рабочему циклу Registry](../CLAUDE.md).

## Уточнение принятого скетча

Добавь `source_image`, запиши одно изменение в `change` и перечисли сохранённые
решения в `preserve`. Например: «Уменьшить высоту кабины примерно на 20 процентов»;
сохранить кузов, шасси, колёсную базу, камеру и освещение.

Агент сначала открывает исходную картинку, затем передаёт её ImageGen вместе
с запросом. Новый текстовый запрос без приложенной картинки не фиксирует прежнюю
компоновку. Результат всё равно нужно сравнить с исходником: уточнение может
изменить части, которые предполагалось сохранить.
Изменение пропорции должно повториться во всех видах. Для нового листа зафиксируй
обновлённые числовые массы и сверь камеры, масштаб и перекрытия по контракту.

Сохраняй новый файл рядом с предыдущим, без перезаписи. После просмотра запиши,
выполнено ли изменение, сохранены ли ограничения и что проверять дальше.
Если поменялась вся конструкция, это новая гипотеза компоновки.

## Действия агента

1. Прочитать задание и шаблон, собрать запрос в новой папке итерации.
2. Для уточнения открыть `source_image` через `view_image` и проверить, что
   запрос относится к этому изображению.
3. Вызвать встроенный ImageGen с аргументами из `imagegen_request.json`.
4. Скопировать полученное изображение в папку итерации. При занятом имени
   выбрать новое имя файла.
5. Открыть сохранённое изображение и проверить предмет, проход, крупные массы,
   ракурс и ограничения. Для исправления выбрать одну наблюдаемую проблему.
6. Обновить `manifest.json`: сохранить путь изображения, статус генерации
   и результат визуальной проверки. Показать пользователю картинку и путь к ней.

Генерация скетча использует встроенный инструмент агента и не требует
подключать API из локального CLI. Переход к отдельному API является самостоятельным
этапом интеграции.

AI изображение помогает выбрать форму. Несколько нарисованных ракурсов могут
противоречить друг другу; они не являются техническим чертежом и не создают
сокеты Registry. Принятую компоновку воспроизведи кубами, назначь размеры
и снимай контрольные виды из одной 3D сцены по
[правилам итерации референсов](REFERENCE_ITERATION.md).
